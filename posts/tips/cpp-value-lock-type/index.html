A value_lock type for C++
Posted June 25, 2026 4 min read

Here’s yet another idea I had for a C++ type. It’s a useful tool for simplifying the use of a mutex with a shared resource.

Before I show you what I made I’ll demonstrate its purpose with a small demo program. I wrote this to intentionally produce errors due to a multithreaded race condition.

 1static pair<int,int>& getPair()
 2{
 3    static pair<int,int> p{0,0};
 4    return p;
 5}
 6
 7int main()
 8{
 9    vector<thread> threads;
10
11    for (int i = 0; i < 10; ++i)
12    {
13        threads.emplace_back([]()
14        {
15            auto& p = getPair();
16            p.first = p.second;
17
18            // sleep here to coax a context switch in the kernel, 
19            // making an error more likely
20            this_thread::sleep_for(chrono::milliseconds(1));
21
22            p.second += 1;
23            if (p.second - p.first != 1)
24                cout << "Hey, that's not right!" << endl;
25        });
26    }
27
28    for (auto& t : threads)
29        t.join();
30    return 0;
31}

Every single time I ran this on my computer it resulted in numerous errors, due to the threads interleaving their increments on the shared pair object. Here’s an example of output, where even the console print instructions fell on top of each other.

This is what you would expect to see, it’s a classic example of bad multithreaded code. Here’s how I fixed it using my new value_lock type.

 1static value_lock< pair<int,int>, mutex > getPair()
 2{
 3    static pair<int,int> p{0,0};
 4    static mutex mtx;
 5    return value_lock{p, mtx};
 6}
 7
 8int main()
 9{
10    vector<thread> threads;
11
12    for (int i = 0; i < 10; ++i)
13    {
14        threads.emplace_back([]()
15        {
16            auto p = getPair();
17            p->first = p->second;
18            this_thread::sleep_for(chrono::milliseconds(1));
19            p->second += 1;
20
21            if (p.second - p.first != 1)
22                cout << "Hey, that's not right!" << endl;
23        });
24    }
25
26    for (auto& t : threads) t.join();
27    return 0;
28}

What gets returned by getPair() holds both a mutex and a reference to the underlying object. On construction the mutex is locked, and on destruction unlocked. In each thread, exclusive access to the underlying reference is guaranteed within the scope of the p variable. This solves the race condition bug in a way that is much more concise and readable than to have used the mutex separately.

My new type has another neat trick, which I borrowed the maybe_ptr type I wrote about previously.

 1static value_lock< pair<int,int>, mutex > getPair()
 2{
 3    static pair<int,int> p{0,0};
 4    static mutex mtx;
 5    return value_lock{p, mtx};
 6}
 7
 8int main()
 9{
10    vector<thread> threads;
11
12    for (int i = 0; i < 10; ++i)
13    {
14        threads.emplace_back([]()
15        {
16            for (auto&& p: getPair())
17            {
18                p.first = p.second;
19                this_thread::sleep_for(chrono::milliseconds(1));
20                p.second += 1;
21
22                if (p.second - p.first != 1)
23                    cout << "Hey, that's not right!" << endl;
24            }
25        });
26    }
27
28    for (auto& t : threads) t.join();
29    return 0;
30}

This solves the problem just as before. Using (abusing) the ‘zero or one’ iterator pattern to create a separate scope in which the underlying resource can be accessed exclusively. This use-case ends up being very powerful if you were to use a type of mutex that is non-blocking. It allows you to say concisely, “Do this if the shared resource can be locked, otherwise do nothing”.

Here’s the actual implementation for value_lock.

 1template<typename T> class value_lock_iterator
 2{
 3public:
 4    using iterator_category  = std::random_access_iterator_tag;
 5    using value_type         = std::remove_const_t<T>;
 6    using difference_type    = std::ptrdiff_t;
 7    using pointer            = T*;
 8    using reference          = T&;
 9
10    constexpr value_lock_iterator(T* p = nullptr) : ptr(p) {}
11
12    constexpr reference operator*() const { return *ptr; }
13    constexpr pointer operator->() const { return ptr; }
14
15    constexpr value_lock_iterator& operator++() { ptr = nullptr; return *this; }
16    constexpr value_lock_iterator operator++(int) { auto tmp = *this; ++(*this); return tmp; }
17
18    constexpr bool operator==(value_lock_iterator const& other) const { return ptr == other.ptr; }
19    constexpr bool operator!=(value_lock_iterator const& other) const { return ptr != other.ptr; }
20
21private:
22    T* ptr;
23};
24
25
26template <typename V, typename M = std::mutex> class value_lock
27{
28public:
29    using iterator          = value_lock_iterator<V>;
30    using const_iterator    = value_lock_iterator<V const>;
31
32    explicit value_lock(V& value, M& mtx)
33        : m_value(value), m_lock(mtx)
34    {}
35
36    value_lock(value_lock const&) = delete;
37    value_lock& operator=(value_lock const&) = delete;
38
39    V& value() { return m_value; }
40    V const& value() const { return m_value; }
41
42    V& operator*() { return m_value; }
43    V* operator->() { return &m_value; }
44    V const& operator*() const { return m_value; }
45    V const* operator->() const { return &m_value; }
46
47    iterator begin() { return iterator(&m_value); }
48    iterator end()   { return iterator(nullptr); }
49
50    const_iterator begin() const { return const_iterator(&m_value); }
51    const_iterator end() const   { return const_iterator(nullptr); }
52
53    const_iterator cbegin() const { return const_iterator(&m_value); }
54    const_iterator cend() const   { return const_iterator(nullptr); }
55
56private:
57    V& m_value;
58    std::lock_guard<M> m_lock; // RAII lock management
59};

I’ve been using this in my most recent project and it has been very useful for me. I’m making my own programming language called Algoma, and I have been using this in the desktop script editor. Algoma scripts need to be executed off the UI thread to avoid potential freezing, and I’ve been using value_lock to mediate resource sharing between UI and runner threads.
