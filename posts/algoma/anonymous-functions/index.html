Anonymous Functions
Posted July 20, 2026 6 min read

Today I implemented anonymous functions for Alogma. It was shockingly easy, and here’s how I did it.

Anonymous Functions are like normal functions except they don’t have an associated identifier, meaning they don’t have a name.

This means implicitly that they declared as expressions, as opposed to declarations and can be easily assigned to variables, passed as parameters, etc…

Many popular languages implement this feature.

Here’s an example from Lua

1local add = function(a, b) return a + b end
2print(add(20, 22))  -- 42

And another from Python

1add = lambda a, b: a + b
2print(add(20, 22))  # 42

As well as Javascript

1const add = (a, b) => a + b;
2console.log(add(20, 22)); // 42

It’s a great feature to have, and with a bit of syntactic sugar it makes writing certain kinds of code a lot easier. I really wanted this for my language.

Testing

Before I got started I generated a test script. The compiler choked on it initially, but that’s exactly what I wanted. It gave me a big list of errors that I could then proceed to fix one-by-one.

Here’s that script:

 1//
 2// Lambda Test 
 3//
 4// Demo / regression test for `fn` lambda expressions (bundle B:
 5// `fn` keyword + `->` arrow, with bare-param and zero-param shortcuts,

 9//   lambda := "fn" params "->" body

11//   body   := expression            // implicit return
12//           | "{" block "}"         // explicit return; nil if none
13//

32// ---------------------------------------------------------------------

Implementation

It was a shockingly easy feature to implement. I managed to get a quick-and-dirty implementation up and running in under an hour.

First I added the new tokens that I’d need, fn and ->

1#define AG_TOKENS(T) \
2    T(FN) \
3    T(MINUS_GREATER) 
4// ...

Then I moved over to the Lexer, and added these new tokens to the relevant parsing code.

 1// ... from Lexer::symbol(char c)
 2        case '-':
 3            if (nextIf('=')) return token(TOKEN_MINUS_EQUAL);
 4            if (nextIf('>')) return token(TOKEN_MINUS_GREATER);
 5            return token(TOKEN_MINUS);
 6
 7// ... from getTokenKind(string s)
 8        case 'f':
 9            if (s.size() > 1)
10            {
11                switch (s[1])
12                {
13                    CASE(2, 'a', "lse", TOKEN_FALSE);
14                    CASE(2, 'o', "r"  , TOKEN_FOR);
15                    CASE(2, 'u', "n"  , TOKEN_FUN);
16
17                    case 'n': return TOKEN_FN;
18                }
19            }
20
21            break;

So far that was pretty trivial, but updating the Compiler would be a bit more involved. The first thing I needed to do was update the list of rules for my Pratt Parser.

1// ... from Compiler::getRule(TokenKind kind)
2R(LESS          , PREC_COMPARISON   , nop        , binary     );
3R(LESS_EQUAL    , PREC_COMPARISON   , nop        , binary     );
4R(FN            , PREC_NONE         , lambda     , nop        ); // <- 
5R(IDENTIFIER    , PREC_NONE         , variable   , nop        );
6R(STRING        , PREC_NONE         , string     , nop        );

The final thing to do was write the actual rule function. As I said previously this implementation is quick and dirty. I can see even now how I want to clean this up later when I’m ready to do a refactor.

 1// ...  from Compiler::lambda()
 2
 3Frame frame;
 4frame.function = m_memory->make<Function>();
 5
 6beginFrame(frame);
 7
 8if (scanIf(TOKEN_LEFT_PAREN))
 9{
10    // try to parse a list of parameters (..., ...)
11    do
12    {
13        if (test(TOKEN_RIGHT_PAREN)) break;
14
15        ++frame.function->m_arity;
16        if (frame.function->m_arity > 255)
17            errorAtPrevious("too many function parameters");
18        int constant = parseVariable(true, "expected parameter name");
19        defineVariable(constant);
20    }
21    while (scanIf(TOKEN_COMMA));
22
23    scanIf(TOKEN_RIGHT_PAREN, "expected ')' after function parameters");
24}
25else if (test(TOKEN_IDENTIFIER))
26{
27    // try to parse a single parameter
28    ++frame.function->m_arity;
29    if (frame.function->m_arity > 255)
30        errorAtPrevious("too many function parameters");
31
32    int constant = parseVariable(true, "expected parameter name");
33    defineVariable(constant);
34}
35
36scanIf(TOKEN_MINUS_GREATER, "expected '->' for lambda function");
37
38if (scanIf(TOKEN_LEFT_BRACE))
39{
40    // block consumes the closing brace
41    block(); 
42}
43else
44{
45    // parse a single expression and emit an implicit RET code. 
46    expression();
47    emitByte(CODE_RET); 
48}
49
50endFrame();

Stated simply, this rule constructs a function using the same machinery that was already in place for named function declarations. The Frame and it’s helper methods manage scope, local variables, upvalues, etc…

The key differences are that there is no name (identifier) to take. There are additional syntactic options for the parameters (zero param, single ident, param list). And if there isn’t an explicit block I create one implicitly using just a single expression.

And that was all I needed to do to run the test script, with all tests passing. Since I’m leveraging the existing mechanisms for functions I didn’t even need to touch the Interpreter, I could completely re-use the existing byte codes.

Beyond even a refactor I can already see that there a few non-critical bugs that I’ll need to address, but otherwise I’m very pleased with the outcome.
